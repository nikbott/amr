# Parallelization Logic: Adapting Adaptive Mesh Refinement for CUDA
*Transformation from Sequential Pointer Reasoning to Parallel Stream Processing*

## 1. High-Level Execution Flow

The flux of the program follows a **Host-Directed, Device-Executed** model. The CPU orchestrates the high-level physics steps, while the GPU retains the mesh data and performs the heavy computational lifting.

### Phase 1: Initialization (CPU)
1.  **Setup**: `main.cpp` parses arguments and initializes the `AMRConfig`.
2.  **Initial Mesh**: A `Quadtree` is created with a single root node.
3.  **Upload**: The initial node (Morton Code 0) is copied to GPU VRAM (`d_codes`, `d_levels`).

### Phase 2: Refinement Loop (CPU Controller)
The main simulation loop in `main.cpp` drives the refinement:
1.  **Call Kernel Driver**: The CPU calls `refineCUDA_pure()`.
2.  **GPU Pipeline Execution**:
    *   **Oracle Kernel**: Parallel Physics check.
    *   **Scan & Scatter**: Parallel expansion of nodes.
    *   **Sort**: Parallel Bitonic Sort.
3.  **Convergence Check**: The GPU copies a single integer (total node count) back to the CPU. 
    *   If `count == old_count`: **STOP**.
    *   Else: **REPEAT**.
    *   *Result: The mesh data stays on the GPU; only 4 bytes moving across PCIe.*

### Phase 3: Balancing Loop (GPU Controller)
To enforce the 2:1 constraint, `main.cpp` calls `balance()`:
1.  **Call Logic Driver**: The CPU calls `balanceCUDA_pure()`.
2.  **Iterative GPU Loop**: unlike refinement, this function contains a loop *inside* the driver (but still on the host).
    *   It launches the **Balance Check Kernel** (neighbors check).
    *   It launches the **Scan/Expand/Sort** pipeline.
    *   It checks convergence after every iteration.

### Phase 4: Visualization (CPU)
1.  **Final Download**: Only when the simulation is 100% complete does `syncFromGPU()` copy the millions of nodes back to system RAM.
2.  **Rendering**: `MeshVisualizer` writes the SVG file using the CPU data.

## 2. The Fundamental Shift: Sequential vs. Parallel logic

The core difference between our CPU and GPU implementations lies not just in hardware, but in the algorithmic approach to state management.

| Feature | Sequential (CPU) | Parallel (GPU) |
| :--- | :--- | :--- |
| **Data Structure** | `std::vector<Node>` (Dynamic) | `uint64_t*`, `int*` (Static Pre-allocation) |
| **Memory Access** | Pointer Chasing / Random Access | Coalesced Streaming |
| **Refinement** | `push_back()` (Amortized $O(1)$) | **scan + scatter** (Global Synchronization) |
| **Logic** | Control Flow Dependent | Data Flow Dependent |

### The Challenge of "Refinement" in Parallel
On the CPU, if a node requires refinement, we simply add 4 new nodes to the end of a list.
On the GPU, thousands of threads run simultaneously. If Node 0 and Node 1000 both decide to refine, they cannot simply write their children to a shared counter without serialization (atomic lock contention), which destroys performance.

**Solution**: We decouple the decision to refine from the action of writing memory.

## 3. The Execution Pipeline: "Map-Scan-Scatter"

Our parallel implementation breaks the single sequential loop into distinct kernels (Stream Compaction).

### Step 1: Logic-Heavy, Memory-Light (Map)
**Kernel**: `evaluateOracleKernel`
**Input**: Current Mesh configuration
**Output**: `bool* results` (Refine/Keep)

Every thread processes one node. This is "Embarrassingly parallel". We calculate physics distances and determine *if* we need to refine. Note that **NO** mesh modification happens here. We only write a definition of intent.

### Step 2: Global Knowledge from Local States (Scan)
**Kernel**: `scanUpSweep`, `scanDownSweep` (Blelloch Algorithm)
**Input**: `int* refine_flags`
**Output**: `int* scan_results` (Offsets)

This is the bridge between parallel threads. Thread $i$ needs to know how many nodes were generated by Threads $0...i-1$ to find its write index.
*   Sequential: `current_offset += count` (Linear dependency)
*   Parallel: Tree-based reduction ($O(\log n)$)

We chose the **Blelloch** recursive pattern over Hillis-Steele because it is **work-efficient** ($O(n)$ operations), making it scalable for large meshes ($>10^7$ elements).

### Step 3: Coalesced Memory Writing (Scatter)
**Kernel**: `expandNodesKernel`
**Output**: `uint64_t* next_codes`, `int* next_levels`

Now, every thread knows exactly where to write.
*   Thread $i$ reads `scan_results[i]`.
*   Writes 1 or 4 nodes to that offset.
*   **Result**: A dense, contiguous array with no gaps and zero atomic contention.

## 4. Data Transfer Strategy (Host-Device)

Minimizing PCIe bus traffic is critical. Our strategy is **GPU-Resident State**.

### Where State Lives
The entire quadtree state (`d_codes`, `d_levels`) stays in GPU VRAM throughout the simulation steps.

### When We Copy
1.  **Termination Check**:
    *   We copy **4 bytes** (the total node count) after the Scan step to check if the mesh size changed.
    *   `cudaMemcpy(&last_scan, ... DeviceToHost)`
    *   If `size == old_size`, we converge; loop terminates.
2.  **Visualization (End of Run)**:
    *   Only when the physics loop finishes do we copy the full arrays back to the CPU for SVG rendering.

This "Compute-on-Device" approach prevents the bandwidth bottleneck ($~16$ GB/s PCI-e) from limiting our compute throughput ($~400$ GB/s VRAM).

## 5. Execution Configuration: Block & Grid Dimensions

### Block Size: 256
We selected a block size of 256 threads.
```cpp
int blockSize = 256;
int gridSize = (n + blockSize - 1) / blockSize;
```

**Rationale**:
1.  **Occupancy**: NVIDIA GPUs (like the T4 or 2080) typically have a limit of 2048 threads per Streaming Multiprocessor (SM). 256 is a divisor of 2048, allowing 8 blocks to be resident on an SM simultaneously.
2.  **Register Pressure**: Smaller blocks (e.g., 256) often allow for better register allocation per thread than maximizing block size to 1024, preventing register spilling to Local Memory.
3.  **Warp Granularity**: 256 is a multiple of the warp size (32), ensuring no threads in a warp are idle due to block boundary alignment.

### Grid Size: Dynamic
The grid size is recalculated every step: `(N + 255) / 256`. 
Since AMR changes $N$ dramatically (from 1024 to $10^7$), a static grid would be inefficient. We launch exactly enough blocks to cover the current active nodes.

## 6. Sorting and Balancing Logic

### Parallel Sorting (Bitonic)
Sequential code uses `std::sort` (Introsort), which is $O(N \log N)$ but strictly serial.
Our kernel uses **Bitonic Sort**, a network of strict comparators.
*   **Sequential Difference**: CPU sort branches based on values. GPU sort compares based on indices.
*   **Why**: This eliminates "Warp Divergence", where threads in the same group wait for each other to finish different code paths.

### Balance Constraint Verification
The most complex logic is the 2:1 balance constraint.
*   **Sequential**: Iterates leaves, does binary search on the `vector`.
*   **Parallel**:
    *   Every thread checks its own neighbors concurrently.
    *   We implement a **Device-Side Binary Search** (`findNodeIndex`).
    *   **Logic**: Each thread acts as an independent reader of the global state. Since state is read-only during this phase, no locks are needed.

By parallelizing the *search*, we turn an $O(N \log N)$ process into an $O(\log N)$ process (depth of logic) executed by $N$ threads.
